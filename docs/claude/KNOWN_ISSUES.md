- KI-006 AI vision reading runs out of output room on a dense page (doc-4 page 1) — **Status: root cause found (b12 diagnostic, 31 Oct), not fixed; owner deferred the fix.**
  - **History:** page 1 hit the cap of 3386 output tokens 3 times (D112, D117 ×2) and fit once (D116). Commit 37cf3b4 (b11) sizes image tokens from each image's real pixels (A4 2944 instead of 3500), raising the cap to 4096 with no window overflow on any measured shape. That fix is correct but not enough: page 1 then filled 4096 twice (requests `01a19437…`, and `01a19441…` from the owner's upright re-upload), each logging `call=page 1 detail=at_output_cap`.
  - **Ruled out (verified):** rotation. Page 1 is a landscape invoice printed on a portrait A4 PDF page. Tesseract OSD already turns it upright (`render.rotation`=270), and OCR of the turned page is readable. The owner's hand-rotated re-upload produced a byte-identical page image (same sha256) and the same failure. Image cost is also ruled out: landscape costs the same input as portrait (3774 tokens).
  - **Ruled out (verified):** a loop. The b12 `vision_answer_shape` line for request `01a19465…` (4096 out): chars 8936, `ws_outside` 4592, `newlines_outside` 601, `longest_ws_run` 9, rows 1, boxes 53, distinct boxes 51. `tail_period=1` there is the cut landing inside indentation, not a loop.
  - **Root cause (verified by those counts):** (1) page 1 makes the AI write about 52 header `fields`, against 7–15 on every other single page on beta (2 pages 21–27, the 5-page invoice 58 in total). There are only 40 allowed names, so at least 12 repeat. The schema puts `fields` before `lines`, so the cap is reached at the first item row. (2) Answers are pretty-printed, about half formatting whitespace (601 line breaks here), which costs hundreds of output tokens on every page, not only doc-4.
  - **Unknown:** which field names repeat and why. Hypothesis: an HSN-wise tax summary table read as repeated `*_total` fields, or many numbers as `other_ref`.
  - **Fix options, cheapest first:**
    1. Log a count per field name (names are the schema's fixed list, safe to log) and make `tail_period` ignore repeats under about 64 characters; then one budgeted retry.
    2. Ask vLLM for compact JSON (no formatting whitespace). This needs the server's vLLM version (a `/version` request to the company server, owner's go). Reading content is unchanged.
    3. Stop the extra fields (prompt or schema rule). This changes readings, so an accuracy run is needed first, as in D92.
    4. Split header fields and item lines into separate calls for dense pages. Most robust, biggest change.
    - Not a fix: a bigger cap (the 8192 server window allows about 4100 at most) or more retries.
  - **Impact:** dense scanned invoices fail AI reading. No wrong values: the document stays on rules and is marked failed.
  - **Repro:** an AI reading of doc-4 on the company vLLM server, then `docker logs reconbench-ai-worker-1 | grep vision_answer_shape`.

## Suspected (unverified)
- Handwriting in the header band (WI-Q2, D93): the band is a fixed crop of the top 35 % of page 1 (`vision_bands.py:51`, `BAND_TOP = 350`), with no check for a mark crossing the cut. A note cut by the edge can be read short, and it is kept beside the page call's full reading because merging only drops exact duplicates (`ai/vision.py:585`, `:589`). Handwriting below 35 % or on later pages gets only the full-page prompt's general rule, not the handwriting-tuned band prompt. No safety effect: handwriting stays in annotations until a person clicks Use as…, and handwritten GRN links stay suggestions (`reconbench_core/mapping/links.py:920–922`). How often either happens on real invoices is not measured. **Owner's plan (31 Oct, for the accuracy work):**
  1. Measure on the local truth set where handwriting appears.
  2. Then smart cropping (cut at a blank row near 35 %) plus an edge guard (drop band notes touching the crop edge).
  3. Only if handwriting is often elsewhere: overlapping bands or targeted crops.
  4. An accuracy run after every change, checking printed fields as D92 did.
- PDFs over 20 pages: the sandbox always calls layout_parse with PDF_LAYOUT_MAX_PAGES=20 (backend/reconbench_app/pdf_sandbox.py:37, :423) while workspace hints allow more; whether pages 21+ raise a visible warning is not checked.
- Scan misdetection (since D107 this also decides which invoices AI may read when the switch is on AI): local_hybrid.py:is_scanned flags a page as scanned when any single image covers ≥50% of it, and that page's text layer is then discarded for OCR (local_hybrid.py `layout`); a digital PDF with a full-page background image would be OCR'd. A text-less page with no large image (e.g. outlined fonts) gets no OCR. Impact on real files not measured.
