## Task 4.2 implementation

- Added configurable weighted line alignment: description, item code, HSN, and UOM produce a four-decimal score; conflicting specs such as `16GB`/`8GB` or `A515-58`/`A315-58` cap the description component; a sorted Hungarian assignment gives a global one-to-one first pass, then qualifying remaining invoice lines may reuse a PO line for split billing. Quantity and rate contribute only to a bounded integer tie-break, never to similarity or eligibility thresholds. Explicit one-line links use the configured lower 0.50 floor; charge lines bypass matching.

### Alignment interpretation recorded for 4.2

The Plan says description blends token-set and token-sort ratios but does not prescribe their relative weights; implementation uses an equal blend. Optional code/HSN/UOM features are scored only when both lines provide them, and the remaining configured weights are renormalized. This avoids treating missing fields as mismatches and is covered by code-level tests; revisit only if the product source documents another interpretation.

## Task 4.3 implementation

- The XML parser uses `lxml.iterparse`, disables DTD loading, entity resolution, and network access, rejects documents with a DOCTYPE, and enforces the configured byte limit. It recognizes Tally-style and generic tags, can accept saved-profile/custom-XPath hints, splits records into separate documents, and saves XPath locators. Unknown tags remain in `extras`.
- The CSV parser checks BOM/UTF-8 first and falls back to `charset-normalizer` (including Windows-1252), sniffs common delimiters, treats every cell as text, searches for the first header row with at least three known synonyms, and groups repeated rows by document number. Unknown columns survive in line extras; a file without a usable mapping returns `CSV_MAPPING_REQUIRED`. Source row ranges are retained.
- Both parsers return the same typed `ParseResult`, warnings, per-field evidence, and a normalized layout signature. Invoice critical fields are checked; missing fields or confidence below 0.70 sets `needs_verification`. `Document.confidence` is the minimum over the invoice critical-field readings (zero when a required reading is missing).
- Arithmetic QA applies the documented ±₹1 checks. When duplicate numeric readings are present, it tries at most 32 alternatives in deterministic source order and keeps only a candidate that reduces the number of failed checks. An unresolved mismatch lowers numeric confidence by 0.30 and produces `EXTRACTION_QA_FAILED`; a recovered alternate produces `EXTRACTION_QA_ALTERNATIVE_SELECTED` for review.
- **Uncalibrated confidence interpretation:** source docs require method-specific confidence but give no base scores or adjustment amounts. This implementation currently uses XML 0.95, CSV 0.90, valid GSTIN +0.03, invalid GSTIN −0.25, ambiguous date −0.15, and passing arithmetic +0.02. These are provisional heuristics, not measured probabilities; calibrate them against anonymized real documents before treating confidence rates as a production-quality metric. Arithmetic-failure confidence reduction is described above.
- Saved layout-profile persistence is not done in the pure parser. The parser accepts `profile`, `custom_xpaths`, and `column_mapping` hints; storage and confirmation are part of the later application integration work.

## Task 4.4 implementation

- Added deterministic vendor resolution in the required order: exact GSTIN, same PAN, normalized exact name, accepted alias, then fuzzy name match. Fuzzy candidates use RapidFuzz `token_set_ratio`; an anchored vendor with one unique score at least 0.92 can be assigned, scores from 0.80 to below 0.92 are suggestions, and ties stay suggestions. A different PAN prevents auto-assignment and sets `merge_allowed=false` on conflicting suggestions. The function returns a `vendor_rule` with the result and does not persist or merge vendors.
- Added the PO-link ladder in phase A: labeled reference (0.99), reverse search through up to six alphanumeric runs (0.97), via GRN/challan (0.95), and explicit manual selection (1.00). Reverse lookup ignores the source invoice number, GSTIN, IRN, e-way bill number, HSN values, and amounts. Missing or cross-vendor cited references stop fallback; rejected PO targets are not recreated.
- Invoice links are represented at line level. One labeled header PO is inherited by invoice lines without their own PO reference. For multiple header PO references, the header references define the content-candidate pool; explicit line references resolve first, then remaining lines are scored individually against those candidates. A line is suggested only at content score >= 0.80 and a lead >= 0.15 over the runner-up; content confidence is capped at 0.90 and therefore remains a review suggestion. If a cited PO is absent from the supplied pool, the result is `NO_PO_LINK` with `PO_NOT_IN_POOL` and the cited number.
- Phase B processes eligible content candidates in invoice date, canonical invoice number, natural-key order. Each accepted suggestion provisionally reserves that line's open quantity and amount before the next line/document is scored. It does not write database state; persistence and worker orchestration belong to later tasks.

### Scoring interpretations recorded for 4.4

The Plan specifies the content-score weights but not each component's exact calculation. The implementation uses weighted invoice amount coverage for line coverage; feasible quantity divided by billed quantity for quantity feasibility; a linear relative-rate agreement score; a binary date signal when both dates exist and PO date is not after invoice date; supported GRN quantity divided by billed quantity; and an exact buyer-GSTIN match only when both sides provide it. These are explicit implementation choices, not measured financial-policy decisions. Fuzzy name matching likewise uses `token_set_ratio` because the source docs do not choose a fuzzy metric.

## Task 4.5 implementation

- Added the pure `evaluate(snapshot, config, run_date)` engine for S1–S7. It consumes a frozen snapshot and explicit date/config; it does not read the database, clock, environment, or network. Inputs, invoice ordering, ledger events, checks, and outputs use stable keys and `Decimal` arithmetic.
- S1 identifies exact duplicates by vendor PAN + canonical invoice number + financial year or matching IRN. A prior invoice with a nearby number, same vendor and taxable value becomes `DUP_SUSPECTED` review. Exact duplicates are blocked from consuming the PO/GRN ledger; suspected duplicates remain reviewable.
- S3 uses the 4.2 line alignment result. Missing or weak alignment cannot become an unflagged match; charge lines bypass goods alignment.
- S4 builds cumulative accepted receipt and billed-quantity ledgers, including opening balances. Accepted quantity is preferred; otherwise received minus rejected is used, or received quantity is treated as assumed accepted with a warning. Eligible quantity is bounded by the invoice quantity and both open PO and GRN capacity. Provisional review cases consume ledger capacity; exact duplicates and rejected invoices do not. `GRN_PENDING` ages to an exception at the configured 30-day threshold.
- S5 checks invoice net rate, arithmetic, invoice taxable total against contract-rate value plus approved charges, cumulative PO value, and unapproved charges. S6 checks tax rate/calculation/slabs, GSTIN and vendor identity, buyer entity, tax type by state, HSN/UOM/currency, date order, late delivery, and payment terms. S7 applies the declared status precedence and returns eligible quantity, payable, at-risk value, GST on risk, blocked duplicate/unlinked value, reasons, evidence, and per-line results. Both payable modes (`pay_at_po_rate` and `hold`) are supported.
- The check registry has stable IDs/versions and feeds `rules_hash`. `partition_components` joins linked invoices, POs, and GRNs, and also joins suspected/exact duplicate invoice pairs so duplicates cannot be split across worker components. `evaluate_components` preserves deterministic result order. `build_run_manifest` records version IDs/config/run date and rules hash, then computes a canonical manifest hash.

### Recorded reconciliation interpretation for 4.5

The Plan's default cumulative `cum_value_vs_po=0` is applied to cumulative **contract-rate value** (`billed quantity × PO rate`) and approved charges. Invoice-rate differences are checked separately by S5 against `unit_rate`. This follows SCN-07, where a +0.3% invoice-rate variance is within the configured 0.5% unit-rate tolerance and must still be Matched; comparing actual invoice amounts to the strict zero cumulative PO-value tolerance would contradict that scenario. This is an implementation interpretation of the Plan's two checks, covered by the SCN-07 test.

The process-pool test compares canonical JSON results after the worker receives and validates serialized snapshots. This verifies pure-core process reproducibility; production task scheduling remains a later application integration task.

## Task 4.9b — required scanned-invoice OCR (G-30)

- The user's scanned invoices make OCR a required pre-pilot part of Phase 4 PDF ingestion. G-30 promotes it from the source plan's P1/v1.1 to this Phase 4 extension. Optional AI extraction in Task 4.17 does not satisfy this requirement.
- Implemented locally: the sandbox first classifies pages, then starts a second child process with its own CPU, memory and wall-time limits for OCRmyPDF + Tesseract on low-text pages. The OCR pass is bounded to selected page ranges, one OCR job at a time, and image-pixel/output-size limits. The original uploaded PDF is never rewritten.
- OCR output is passed through the existing PDF extraction, normalization, field-evidence, critical-field and arithmetic-QA path. OCR-touched page text is persisted with `document_text.is_ocr=true`; the document version uses `pdf_ocr`; fields evidenced on OCR pages receive a provisional 0.10 confidence reduction. The Preview labels OCR-assisted extraction. The default Tesseract language is English; the worker image also includes Hindi trained data and `RB_PDF_OCR_LANGUAGES=eng+hin` enables both.
- OCR text alone does not mark a document Matched. Missing or low-confidence critical fields and any unreadable pages remain Needs Verification / Needs Review. OCR unavailability, timeout, or no recovered text preserves the original `NO_TEXT_LAYER` review item with an explanatory warning.
- **Status: the isolated OCR path has synthetic execution evidence; real-layout accuracy is unverified.** A new image-only invoice fixture exercised `parse_pdf_isolated` and recovered invoice number, date and taxable value with OCR page evidence and the expected confidence penalty. Tesseract misread the GSTIN, which was rejected by checksum validation and left the document flagged for verification. The backend Docker image has OCRmyPDF 17.13.0 and Tesseract 5.5; its trained-data configuration includes `eng`, `hin` and `osd`. No real sample was opened. G-07 representative scans and hand-labelled field truth are still needed to measure OCR accuracy across suppliers/languages and calibrate confidence.

## Invoice-first matching audit and acceptance guardrails

The governing product rule is PRD §0 and §7.4: an invoice is the case anchor; POs and GRNs are evidence found for that invoice. The PO-line ledger is used to enforce cumulative ordered, received, and billed quantities across invoices. A PO-ledger implementation detail does not make the case flow PO-centric.

- Every active, successfully parsed invoice included in a reconciliation run must produce exactly one invoice case and an explainable outcome. A case can be Matched, Matched with flags, Pending, Exception, Duplicate, Needs Review, or Unlinked. “Every invoice gets an answer” does not mean every invoice is safe to auto-link or auto-match.
- A low-confidence or ambiguous candidate must remain Suggested / Needs Review or Unlinked with candidate evidence and a reason. Do not lower a threshold or fabricate a link to increase the match count; the PRD explicitly prioritizes precision and forbids silent false Matched results.
- POs and GRNs support invoice cases. They should be shown as linked evidence or surfaced as unlinked/orphan records in the relevant mapping/report view; they are not separate payable cases.
- Current deterministic “semantic” matching is field-aware similarity: normalized descriptions plus available item code, HSN, UOM, and specification-conflict checks. Content-based PO ranking also uses quantity feasibility, rate, dates, GRN support, and buyer GSTIN. It is auditable lexical/structured matching, not an embedding or general-purpose language-model interpretation.
- Content suggestions require score >= 0.80 and a lead >= 0.15 over the next candidate; their confidence is capped at 0.90 and they require review. These existing PRD defaults remain unchanged. AI hooks may help with ambiguous descriptions/candidate ranking later, but must not calculate financial checks, overrule specification/vendor conflicts, or silently change a verdict.
- The reviewed field dictionary has no populated real-document synonym list. The supplied DBC PO/GRN XMLs and scanned invoice PDFs have now been inspected, but they are not a representative hand-labelled golden set: the DBC exports lack item descriptions and PO references, while the scanned PDFs still have no extracted line items. Broad supplier/layout coverage and the PRD’s precision/recall targets are therefore not demonstrated. Add aliases only from reviewed evidence; calibrate against a representative, hand-labelled golden set before making production accuracy claims.

These guardrails add no new finance policy and do not change the six source Markdown documents, schema, thresholds, or engine behavior. Tasks 4.13–4.18 must preserve them in the run API, case views, export, and acceptance evidence.
